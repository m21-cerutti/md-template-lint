# ADR 0003: pnpm as the exclusive package manager

pnpm (v11.16.0+) is the sole package manager for this project.

## Context

The project started with npm and `package-lock.json`. npm is the Node.js default but
lacks strong monorepo support. pnpm provides:

- Stricter dependency resolution (no implicit access to transitive deps).
- Content-addressable store (less disk duplication).
- Built-in workspace support for future monorepo scaling.

The project may scale to a monorepo, and pnpm is suited to that growth.

## Decision

The project uses **pnpm@11.16.0** (pinned in `package.json` `packageManager`).
All scripts and docs reference pnpm, not npm (CI is added later and will use pnpm too). Registry-level commands such as `npm publish` stay a human step.

**Lifecycle scripts policy:** pnpm blocks dependency lifecycle scripts
unless they are approved (build approval list `allowBuilds`; verified by the clean
`pnpm install --frozen-lockfile` run). This project has no dependencies that
require builds: all are pre-built or pure JavaScript. The policy is explicit:
`allowBuilds: {}` in `pnpm-workspace.yaml` documents "no builds allowed", matching
the default behavior and making the decision auditable.

**Publishing:** `npm publish` remains a human step; agents never publish (opencode.jsonc deny rule).

## Consequences

- `node_modules` is strict: importing an undeclared (phantom) dependency fails at run time, when the module is resolved.
- All scripts and CI use `pnpm install --frozen-lockfile` and `pnpm run`.
- `pnpm-workspace.yaml` documents lifecycle script approval explicitly.

## Alternatives considered

| Option | Pros | Cons | Verdict |
| --- | --- | --- | --- |
| **pnpm** | Strict deps, content-addressable store, workspace-ready | Requires explicit build approval | **Chosen** |
| npm | Default, bundled with Node | Loose deps, weak workspace support | Rejected |
| yarn | Workspaces, deterministic | Slower, less strict | Rejected |
